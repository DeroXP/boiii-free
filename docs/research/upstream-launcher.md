## Summary

Pre-boot flow: boiii.exe main() (src/client/main.cpp:992-1108) first works out the game folder from the current directory, game_path.txt or Steam auto-detection. It then runs the self-updater synchronously against https://r2.ezz.lol, and only after that shows the launcher window, which is just HTML. When the player presses PLAY with no launch options, the launcher window closes and the same process goes on to map BlackOps3.exe into memory and start it. If any launch option is chosen, it instead starts itself again with `-launch -<opt>...` in a new process. If a "keep launcher" mode or a pinned version is chosen, it starts a separate process: the same exe with `-launch`, or <game>/versions/boiii-<tag>.exe. Nothing in the launcher UI (main.html 130 KB, main.js 154 KB, main.css 76 KB, a 1.2 MB background JPEG, verification.json) is built into the exe. All of it lives in %LOCALAPPDATA%\boiii\data\launcher and the updater keeps it in sync. On first run the update is forced, so the launcher cannot start without internet the first time (main.cpp:895-898, 1049-1058).

Rendering and bridge: the main engine is WebView2. The SDK is vendored at 1.0.4191.47 and linked statically; it needs the Evergreen runtime. Legacy MSHTML (CLSID_WebBrowser / Wine Gecko) is used only under Wine or when WebView2 returns E_NOTIMPL. Any other WebView2 failure shows an error box and the process exits. The bridge is a synchronous IDispatch host object named `external`. JS reaches it through `chrome.webview.hostObjects.sync.external`, wrapped in a Proxy that sets `__request` to JSON {name,args} and then reads `__response`. C++ registers 60 named callbacks (47 in launcher.cpp, 13 in launcher_workshop.cpp). There is no way for C++ to push events to the page, so every long task runs on a detached thread and the page polls for status every 100-500 ms. The UI is one ~4.5k-line IIFE in mostly-ES5 JS with these pages: Home (PLAY, 15 launch-option toggles, version picker, player name), Workshop (quick download, scraped browse/search, item modal), Library (installed items, check updates, delete), Friends (local friend codes only), and Settings with 6 tabs (General, Graphics, Asset Pools, Patches, Binds, Diagnostics). There are also popups for Manage, Verify, Message, Confirm and Credits. There is no server browser, no mod load order and no packs. Settings are spread over properties.json, WebView2 localStorage, launcher_settings.json, config.cfg and config.ini (edited by string find/replace), plus file renames for some toggles.

Updater: the manifest is a JSON array of [name,size,SHA1] covering boiii.exe and data/**, generated by CI. Integrity rests only on TLS plus size and SHA-1; nothing is signed. Executables are written to a .new file, re-verified, and swapped in with MoveFileEx. The running exe is renamed to .exe.old and the process relaunches itself. The update runs twice per launch: synchronously before the launcher, and again in the updater component thread during component activation. On every successful manifest fetch it deletes any entry at the %LOCALAPPDATA%\boiii root other than user/ and data/, and any file under data/ that is not in the manifest. Critical for Xerces: the manifest entry "boiii.exe" maps to the path of whichever exe is running, so as written the upstream updater would overwrite a renamed Xerces build with upstream boiii.exe. It also runs on first launch even when -noupdate is passed. The fork already had to stub update() for this reason (DeroXP e5968d07). The version picker downloads GitHub-release or R2-beta exes into <game>/versions and runs them with no hash check.

Workshop and verification: the launcher downloader bootstraps SteamCMD into <game>/steamcmd and runs `+login anonymous +workshop_download_item 311210 <id> validate +quit`. It retries up to 20 times and installs to <game>/mods|usermaps/<id>/zone. Progress is measured from folder sizes and system-wide network counters. Browse and search scrape steamcommunity.com HTML, then read details from the public GetPublishedFileDetails Web API. There is no dependency handling. The in-game downloader (steamcmd.cpp, plus the ImGui download_overlay drawn in a Present hook) uses a different SteamCMD command and a different folder layout. Verification is a report-only xxh3 check against verification.json (1598 files, 134 GB, components base/sp/zc/dlc/redist), which matches the current Steam exe. On this PC the installed BlackOps3.exe (PE CheckSum 0x6531394, SHA-1 9D03F810…) is the build upstream supports. It is byte-identical to the archive.org copy that the "patch installer" offers to users whose exe differs.

Code-read defects that matter for the redesign:
- First-run Steam detection has a regression from commit 7ec674581: the default-path check is inverted. If BO3 is not in the default library and boiii.exe is outside the game folder, main() loops forever. The fallback "Game Setup" page calls `window.external.*`, which WebView2 does not provide.
- The SteamCMD stdout pipe is never read, so downloads can stall.
- `openUrl` passes any string to ShellExecuteA.
- No navigation allowlist is set.
- The friends-only setting and the workshop_timeout setting are never used.
- The skip-intro toggle renames .mkv files that verification then reports as missing.

For Xerces, reuse the WebView2 window host, the verification engine and the core of the updater's replace/rollback logic. Replace the UI, the sync bridge (move to async messaging), the settings model, the Workshop scraping, the version picker, the archive.org exe installer and the updater's endpoints, trust model and cleanup.

# Upstream pre-boot stack (local branch `xerces` = upstream 5aa7fac)

## 1. Web engine and JS <-> C++ bridge

**Engines (both, with fallback)**
- **WebView2** (Chromium/Edge Evergreen runtime) is the default.
  - SDK vendored at `deps/Microsoft.Web.WebView2` 1.0.4191.47 (commit 097557ba), linked as `WebView2LoaderStatic` (`deps/premake/Microsoft.Web.WebView2.lua:11`).
  - Environment and controller are created asynchronously in WM_CREATE (`html_window.cpp:114-117` -> `html_frame.cpp:204-263`).
  - The URL is queued until the controller is ready (`html_frame.cpp:291-297, 370-372`).
  - User data folder: `%LOCALAPPDATA%\EZZ BOIII\WebView2` (`html_frame.cpp:49-60`).
- **Legacy MSHTML** `CLSID_WebBrowser` ActiveX (Wine Gecko under Wine) is used only if `utils::nt::is_wine()` or WebView2 returns `E_NOTIMPL` (`html_frame.cpp:210-214, 310-334, 430-466`).
  - The security manager maps every URL to `URLZONE_TRUSTED` (`internet_security_manager.hpp:228-231`).
- Any other WebView2 error shows a MessageBox, then WM_CLOSE, then the process exits (`html_frame.cpp:300-308`, `main.cpp:1064-1066`).

**Protocol**
```
JS  main.js:415-455
  raw = chrome.webview.hostObjects.sync.external        // WebView2
  getExternal()[name](...args) => { raw.__request = JSON.stringify({name,args}); return raw.__response; }
  fallback: window.external (MSHTML)
C++ html_frame.cpp:62-186 (webview_dispatch : IDispatch, AddHostObjectToScript(L"external"))
  DISPID 0x60000000 "__request"  -> parse JSON, args: string->BSTR, bool, int->I4, number->R8, else EMPTY
                                  -> callbacks_[name](args) -> response_ VARIANT
```

## 5. First-run behaviour

1. **Game path lookup** (`main.cpp:694-893`):
   1. cwd is a valid game folder.
   2. `%LOCALAPPDATA%\boiii\user\game_path.txt`.
   3. `find_steam_game_path()`: default `<local scratch copy, not kept>\Program Files (x86)\Steam\steamapps\common\Call of Duty Black Ops III`, then `HKLM\SOFTWARE\WOW6432Node\Valve\Steam\InstallPath` (`steam/steam.cpp:131-150`), then line-based parsing of `libraryfolders.vdf`.
   4. "BOIII - Game Setup" window (480x300, WebView2) with a folder picker.
2. **Regression (7ec674581)**: `if (!is_valid_game_folder(default)) return default;` is inverted (`main.cpp:649-651`).

3. **Setup page**: its inline JS calls `window.external.openFolderPicker()`, which is not the WebView2 host object, so the button is broken under WebView2 (`main.cpp:866-885`).
4. **Initial data**: the update is forced. Without network the launcher cannot start.
5. **Other first-run effects**:
   - The WebView2 user-data folder is created.
   - The ECC identity key is generated when the Friends identity is read.
   - `config.ini` does not exist until the game has run once, so graphics settings return "no_config".
   - properties.json writes can be lost while `<game>/boiii_players` is missing.
6. **Error string to rename**: `game/base.cpp:13-14` throws "Make sure you place Boiii.exe next to BlackOps3.exe!" if the engine base is queried before the game is loaded. `try_refresh_workshop_content` catches it.

## 7. Updater

**Manifest**
- Format: `[["boiii.exe",size,"SHA1"],["data/...",size,"SHA1"],...]`, generated by CI (`build-and-publish.yml:101-123`; beta in `build-and-publish-beta.yml:86-107`).
- URLs: `https://r2.ezz.lol/boiii.json?<ns>` or `boiii-beta.json`.
- Files: `.../boiii/<name>?<sha1>` or `.../boiii/beta/<name>?<sha1>`.
- User-Agent `ezz-updater/1.0`. GET requests set no timeout; only retries.

**Flow** (`file_updater.cpp:190-253`)
1. Delete `.exe.old`.
2. Create the empty CoD config.ini if missing.
3. Fetch the manifest.
4. **Cleanup** (637-713): delete root entries other than user/, data/ and exact manifest names; delete files under data/ that are not in the manifest.
5. Find outdated files by size then SHA-1.
6. Update the host exe: rename to .old, download and verify, relaunch, terminate.
7. Download the other files in parallel (about 2/3 of cores).
8. Exe files are written as `.new`, verified, then moved into place with MoveFileEx.

**UI**: a custom GDI progress window titled "BOIII Updater" (`progress_ui.cpp`). It runs headless for a dedicated server or with -headless. Errors show a MessageBox titled "Updater Error".

| Condition | Pass 1 (`main.cpp:1046`, blocking) | Pass 2 (component thread, `component/updater.cpp:283`) |
|---|---|---|
| default | runs | runs |
| autoUpdate=false | only if forced (first run) | skipped |
| -noupdate | only if forced | skipped |
| -update / -beta | runs | runs |
| another BlackOps3.exe/boiii.exe running | skipped | runs |
| dedicated | skipped | runs (headless) |

- Debug builds skip updating the host exe unless -update is passed.
- If selectedVersion is not "latest", the host exe is not updated.
- **Fork note**: e5968d07 stubbed `update()` because it overwrote the custom build.

## 8. Workshop downloader

**Launcher path** (`launcher_workshop.cpp:1453-2476`)
1. Refuse if an in-game download is running.
2. Return early if `find_installed_workshop_item` finds an existing install, unless this is an update. It checks mods/usermaps/<id>/zone, Steam's content folder, workshop.json IDs, then a Web API title.
3. Bootstrap SteamCMD: download steamcmd.zip from the Steam CDN (no hash); if the exe is under 3 MB, run `+quit` hidden for up to 180 s.
4. `GetPublishedFileDetails` returns title and size, with an HTML scrape as fallback. Require 2 x size + 512 MB of free disk.
5. Delete `./steamcmd/steamapps`.
6. Run `steamcmd.exe +login anonymous +workshop_download_item 311210 <id> validate +quit`. The window is hidden and stdout goes to a pipe that is **never read**.
7. Progress comes from the size of downloads/content/311210/<id> (four candidate paths), the bootstrap and workshop logs, system-wide `GetIfTable2` byte counters, and an ETA estimate.
8. A side thread watches `content_log.txt` and clears the staging folder when the download starts (purpose inferred: undo pre-allocation for size-based progress).
9. Retry and abort rules:
   - Up to 20 attempts, then a MessageBox asking to continue.
   - 5 attempts that fail in under 15 s trigger a wipe of the SteamCMD cache folders.
   - Pause terminates the process; Resume restarts it.
   - Cancel terminates and deletes partial files.
10. Install:
    - Type comes from `workshop.json` or Web API tags.
    - Destination: `<game>/{mods|usermaps}/<id>/zone` (named by ID).
    - Copy with progress, delete staging, set `PublishedFileId` in workshop.json.
    - Check for .ff/.sabl/.sabs/.pak/.xpak files.
    - Send `userContentReload`.

**Listing and browse**
- Browse scrapes up to 20 pages of `steamcommunity.com/workshop/browse?appid=311210&browsesort=mostrecent&section=readytouseitems` with 200 ms between pages.
- Search scrapes up to 10 `textsearch` pages, with a 10-minute cache.
- Details come from `api.steampowered.com/ISteamRemoteStorage/GetPublishedFileDetails/v1/` (no key) in batches of 20, filtered to consumer_app_id 311210.
- Library update flag: `time_updated > folder mtime`.
- Dependencies: **none**.

**In-game path** (`steamcmd.cpp`)
- Triggered from `workshop.cpp` (830-945, 1194) when content is missing.
- Command: `+login anonymous app_update 311210 +workshop_download_item 311210 <id> validate +quit`, waiting forever.
- Moves the item to `./mods/<id>` or `./usermaps/<id>` with **no zone/ subfolder**.
- Progress is drawn by the ImGui download overlay. After success it offers to reconnect to the server.
- Under Wine it fetches `steamcmd_linux.tar.gz` and extracts it with `system("tar ...")`.

## 9. Install verification

- `verification.json` structure:
  - `ManifestHash` (unused).
  - `components` (redist, base "Base Game (MP/ZM)", sp, zc, dlc, each with displayName/show/required/defaultEnabled/totalSize).
  - `files[[path,size,xxh3,component]]`: 1598 entries, 134 GB.
- Flow (`launcher.cpp:251-599`):
  1. Choose a mode: all, zm_, mp_, cp_.
  2. Filter by component (redist skipped; dlc counts for MP or ZM) and by `cp_/mp_/zm_` and `en_*` filename prefixes.
  3. Per file: existence, then size, then XXH3-64 with a 16 MB buffer (only when the size matches).
  4. dlc and zc problems are warnings; base and sp problems are errors.
  5. Output: a summary string plus a `[severity] path (missing|wrong size|corrupt - Component)` list.
- The manifest is pinned to the current Steam build (BlackOps3.exe 106059256 bytes) and is refreshed by the updater.
- It is report-only: there is no repair action and no link to Steam's own verify.

## Design implications

- Before shipping any Xerces build: change UPDATE_SERVER, the manifest names, UPDATE_HOST_BINARY and the User-Agent, or disable the updater until Xerces has its own channel. Add Ed25519-signed manifests with SHA-256, curl connect and total timeouts, and a single update pass that does not block, running after the window appears.
- Limit updater cleanup to a folder the updater owns (for example %LOCALAPPDATA%\Xerces\app\). Never store mods, packs, profiles, plugins or identity keys under updater-managed folders.
- Keep WebView2 but replace the synchronous IDispatch host object with an asynchronous JSON-RPC bridge that can push progress for downloads, verification, update and game state, replacing the more than 20 polling loops. Serve the UI from SetVirtualHostNameToFolderMapping (an https virtual origin) instead of file://. ## Risks

- The upstream updater would overwrite any Xerces exe with upstream boiii.exe, because the 'boiii.exe' entry maps to the running exe's path (file_updater.cpp:536-543). It also runs on first launch even with -noupdate (main.cpp:1046). This must be changed before any Xerces build runs (precedent: fork commit e5968d07).
- Updater cleanup deletes data: on each successful manifest fetch it removes unknown entries at the %LOCALAPPDATA%\boiii root (including plugins/, minidumps/, dumped_lua/) and any file under data/ that is not in the manifest (file_updater.cpp:637-713). Xerces mods, packs or profiles kept there would be wiped.
- Nothing in the update chain is signed. The manifest uses SHA-1 and trust rests only on TLS to r2.ezz.lol, so whoever controls that bucket controls code execution. The version picker and beta paths download and run exes with no hash at all (launcher.cpp:1342-1353, main.cpp:935-948), and the exe URL comes from page JS through the bridge.
- The bridge function openUrl calls ShellExecuteA("open") on any string. Workshop descriptions turned into HTML can carry [url] links to local or UNC executables that run on click (launcher.cpp:1491-1504, main.js:329-356). There is also no WebView2 NavigationStarting allowlist, and the host object is exposed to whatever page is loaded.
- First-run detection has a regression (inverted default-path check, commit 7ec674581) that can spin main() forever with no UI. The fallback setup page is effectively unreachable, and it is also broken under WebView2 (main.cpp:649-651, 866-885, 1030-1036).
- A blocking network call runs before any UI with no curl timeouts. The update also runs twice, adding a second manifest fetch on the way into the game (main.cpp:1046; component/updater.cpp:283-289; http.cpp:87-160).
- SteamCMD downloader problems: the stdout pipe is never drained, so downloads can stall; ./steamcmd/steamapps is deleted before every download, so nothing resumes across sessions; launcher and in-game downloaders use different commands and folder layouts (zone/ vs root); the browse feature scrapes steamcommunity.com HTML, which is fragile and may conflict with Steam terms; it can delete Steam-managed workshop content; and nothing resolves item dependencies.
- Settings are spread across 5 or more stores and config files are edited by string find/replace. Some toggles do nothing (friends_only, workshop_timeout). properties.json writes can be lost before <game>/boiii_players exists.
- Legal and branding exposure: the code downloads the copyrighted game exe from archive.org (main.cpp:127-132, 334-504), the Patches tab is out of date and links an older exe (main.html:2744-2790), and the splash and launcher background use official Activision key art.
- Feature conflict: 'Skip intro' renames .mkv files that verification.json expects, so verification then reports errors for those files.
- The running-game check matches only the names boiii.exe and BlackOps3.exe, so a rename breaks it and versioned exes (versions/boiii-*.exe) go undetected (launcher.cpp:1423-1459).
- ANSI Win32 APIs (GetCurrentDirectoryA, SetCurrentDirectoryA, CreateProcessA, va("file:///%ls")) make non-ASCII game or profile paths fragile.
- Keep-launcher mode leaves WebView2 processes, a 20 fps canvas animation and polling timers running during gameplay, a perf cost the Xerces perf goals would need to avoid.
- download_overlay owns the only Present hook and MinHook refuses a second one (fork bfca64a6), so a DX11 upscaler or perf overlay that installs its own hook will clash.
